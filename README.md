# Automated tests

Ten end-to-end UI tests for `minicast-release.apk`, driven through Appium from Python.
They run on an Android emulator in GitHub Actions on every push.

Everything here runs from this directory, not the repo root.

```bash
cd automation
uv sync
export ANDROID_HOME=$HOME/Library/Android/sdk   # the Appium server needs this too
appium --relaxed-security &
uv run pytest -v
```

**Last run on a physical device (CPH2491, Android 16): 7 passed, 3 xfailed, exit 0 — 4m26s.**
The three xfails are open defects, described below.

### What it handles

Status is what has actually been run, not what the code implies.

| | Status |
|---|---|
| Android, physical devices and emulators | run on both |
| Device selection by serial, model, `virtual` or `real` | run |
| Parallel across devices (`pytest-xdist`), one per worker | run on 1 phone + 1 emulator, 2m43s vs 4m42s |
| Allure reports, with the device on every result | run |
| Screenshot, page source and logcat attached on failure | run |
| Playback state, position and speed from the media session | run |
| Sound genuinely reaching the audio output (`dumpsys audio`) | run |
| Known defects held as `xfail(strict=True)` | run — three of them |
| Static checks: `ruff` and `mypy`, including test bodies | run, in CI before the emulator |
| iOS simulator and device discovery (`simctl` / `xctrace`) | discovery run; **no iOS session ever opened** |
| iOS page objects, locators and capabilities | written, **never executed** |
| Audio frame counts (`dumpsys media.metrics`) | implemented, **no test uses it** |
| Audio *content* — waveform capture, number recognition | **not implemented** |
| CI on a GitHub Actions emulator | written, **never run** |

The last four are the honest gaps. The iOS path is structure so that adding a build is a config
job rather than a rewrite; it is not a working iOS suite. Audio is verified as *present*, not as
*correct* — checking the spoken number would mean capturing the emulator's audio and
transcribing it, which is described in "How playback is verified" and deliberately left out of
the gate.

### Why three tests are expected to fail

Tests 4, 6 and 9 are `xfail(strict=True)` against known defects:

- **BUG-001** (Sev 2) — pausing in the app leaves the media session reporting `PLAYING`, so the
  lock screen and notification show the wrong state.
- **BUG-003** (Sev 2) — one global playback position is applied to whatever episode you open next,
  so a never-played episode can open at its end.
- **BUG-005** (Sev 1) — the +15s control advances 30 seconds.

Severities are set in [`../docs/BUG_REPORTS.md`](docs/BUG_REPORTS.md), which is the source of
truth for them.

Asserting the buggy behaviour would quietly bless it. Asserting the correct behaviour turns CI
red. `strict=True` does neither: CI is green today, and the moment either bug is fixed the test
**fails**, forcing the marker off. The defect stays visible in the report instead of in a backlog.

### How playback is verified

Three signals per playback test, so a UI that lies gets caught:

| Signal | What it proves |
|---|---|
| Position label | what the app shows |
| `dumpsys media_session` | position, state and speed the platform holds |
| `dumpsys audio` | a player is genuinely writing to the audio output |

Speed is measured against wall clock (12s real → ~24s of media at 2x), so a label-only
speed change fails.

**Audio content is not asserted.** The spoken counting could be verified by capturing the
emulator's audio and transcribing it with a number-word grammar, but that needs a PulseAudio
sink on the runner and that can be flaky to start with. There is a `@pytest.mark.audio`
marker reserved for it; nothing uses it yet, and it would go in a separate non-blocking job.

### Layout

```

minicast/devices.py           find and choose the target device
minicast/driver.py            capabilities and session creation
minicast/pages/               page objects - each owns its locators, plus the factory
minicast/probes/              PlaybackProbe protocol + Android/iOS implementations
                              (probe_for() enforces the protocol; mypy checks signatures)
minicast/support/             adb wrapper, bundled catalog data
tests/                        the nine tests
```

#### Pages and locators

Each page owns its own locators as a class attribute, keyed by platform:

```python
class Discover(BasePage):
    LOCATORS = {
        "android": {"search_field": tag("searchField")},
        "ios":     {"search_field": a11y("searchField")},
    }
```

`build_pages(driver, platform)` returns a `Pages` dataclass holding all four, so tests read
`pages.discover` rather than a dict lookup. Python's Selenium has no PageFactory - the `@FindBy`
proxies are a Java/C# feature - so this is the conventional equivalent rather than a hand-rolled
imitation of it.

A session fixture calls `check_locator_parity()` and fails the run if a page defines a name on
one platform but not the other.

Two things caught me out here, both verified against a live session:

- **`AppiumBy.ID` does not work on this app.** Compose test tags surface as *bare*
  resource-ids (`searchField`), and Appium's ID strategy qualifies the name with the package
  before matching. `UiSelector().resourceId("searchField")` matches, and is faster than the
  XPath equivalent, so that is what the Android map uses.
- **The transport buttons carry no text or content-desc of their own** — the label sits on a
  child node. `playPauseButton.get_attribute("content-desc")` is always empty. Paused state is
  read from the accessibility id `Play`, and the speed value by looking for `1x`/`1.5x`/`2x`
  on screen.

`ACCESSIBILITY_ID` is still preferred where it exists, because it maps to `contentDescription`
on Android and `accessibilityIdentifier` on iOS. If the developers set both from one constant,
the two locator files collapse into one.

#### Rows have no ids

Show cards and episode rows carry no test id, and their text sits in a non-clickable child.
`BasePage.tap_row()` finds the text and climbs to the nearest clickable ancestor. It is the
one brittle thing in the suite, deliberately kept in one place. Asking for `showCard_<id>`
and `episodeRow_<id>` is the single highest-value testability change the developers could make.

#### iOS

`config/ios.yaml`, `locators/ios.py` and `IOSProbe` exist so adding iOS is a config job rather
than a rewrite. **None of it has ever run** — there is no iOS build. `IOSProbe` skips the
calls it cannot answer instead of faking them.

### Running locally

Prerequisites: Python 3.11+, `uv`, Node 20, Java 17, Android SDK platform-tools, and a
connected device or booted emulator.

```bash
uv sync
npm install -g appium@2
appium driver install uiautomator2

# Appium needs the SDK on its own environment, not just yours.
export ANDROID_HOME=$HOME/Library/Android/sdk
appium --relaxed-security &
```

#### Choosing a device

With one device connected you need nothing. With several, `--device` takes a serial, a
case-insensitive model substring, or `emulator` / `real`:

```bash
uv run pytest --device 8TUSGEXOQWQSQ4WS   # exact serial
uv run pytest --device cph                # model substring
uv run pytest --device emulator           # first emulator
```

Ambiguity is an error, not a guess:

```
RuntimeError: 2 devices connected, so the target is ambiguous.
Pass --device <serial|model|emulator|real>:
  8TUSGEXOQWQSQ4WS (device: CPH2491, Android 16)
  emulator-5554 (emulator: sdk_gphone64_arm64, Android 14)
```

`minicast/devices.py` resolves the choice once and exports `ANDROID_SERIAL`, so Appium and the
adb-based probe are guaranteed to talk to the same handset. They are configured separately, and
before this they could silently diverge - Appium driving one phone while `dumpsys` read another.
`ANDROID_SERIAL` is still honoured as the default if you prefer to export it.

iOS resolves the same way, through `simctl` for simulators and `xctrace` for physical devices:

```
B1AB37C5-...-5332C4A99614 (simulator: iPhone 15 Pro Max, iOS 17.5, Booted)
00008130-000E20942642001C (device: Nitish's iPhone, iOS 26.5)
9CA958AE-...-270C255FFB53 (simulator: iPhone 15, iOS 17.5, Shutdown)
```

With no selector a booted simulator wins over a shut-down one. Matching goes exact serial,
then exact model, then substring - so `--device "iPhone 15"` gets you the iPhone 15 and not
the Pro Max that happens to be running.

### Running in parallel

`pytest-xdist` spreads the suite across devices. Each worker takes one:

```bash
uv run pytest -n 2                                  # every connected device
uv run pytest -n 2 --device "iPhone 15 Pro Max,iPhone 15"
uv run pytest -n 4 --device emulator-5554,emulator-5556
```

Workers map round-robin, so more workers than devices is allowed - they just share. Each
session gets its own helper ports (`systemPort` and `mjpegServerPort` on Android,
`wdaLocalPort` on iOS), because two UiAutomator2 sessions on one port is the usual reason a
parallel run dies at the second session.

Unbooted simulators are left out of an unselected pool; booting several at once is not
something to do by accident. Name them explicitly if you want them.

xdist captures worker logs, so a parallel run does not print which device took which test.
Every Allure result carries `device` and `serial` labels instead:

```
CPH2491 [8TUSGEXOQWQSQ4WS] - 3 tests
sdk_gphone64_arm64 [emulator-5554] - 5 tests
```

Measured on one handset plus one emulator: **2m43s parallel against 4m42s serial.**

#### Selecting tests

```bash
uv run ruff check . && uv run mypy     # static checks, no device needed
uv run pytest -n 2                     # in parallel, one device per worker
uv run pytest -v                       # everything
uv run pytest -m smoke                 # 3 tests, ~90s: browse, play, background
uv run pytest -m regression            # the full suite
uv run pytest -m playback              # anything that starts audio
uv run pytest -m known_bug             # just the open defects
uv run pytest -m "not android_only"    # the cross-platform subset
uv run pytest -k search -v             # by name
uv run pytest --no-install             # skip the reinstall (faster; see below)
uv run pytest --reruns 1 --reruns-delay 3
```

#### Devices that refuse `pm clear`

By default Appium reinstalls the app, which wipes its data and gives each run a clean profile.
Some manufacturer builds refuse `pm clear` outright (`SecurityException: ...
CLEAR_APP_USER_DATA`) - and since that is what Appium calls during reset, the session cannot
start and every test errors at setup.

The driver fixture detects that one error and retries with `noReset`, logging a warning. No
flag needed. `--no-install` is still there to skip the reinstall deliberately, which is faster.
CI runs on an emulator where `pm clear` works, so it installs normally and the warning never
appears.

With `--no-install` the app keeps its state between runs, so every test is routed back to
Discover before it starts, and the playback tests wind the position back to the start of the
track rather than assuming 0:00 — the app carries a position between episodes (BUG-003).

#### Allure

```bash
uv run pytest                 # writes allure-results/
allure serve allure-results
```

Failures attach a screenshot, the page source and the tail of logcat automatically.
Each test is tagged with the manual case ids it covers, so the report maps back to the plan.

### CI

Two files: [`.github/workflows/e2e.yml`](.github/workflows/e2e.yml) is the job,
[`automation/ci/run_e2e.sh`](automation/ci/run_e2e.sh) is everything that happens once the
emulator is up. Triggered on every push and pull request. It extends the starter workflow
provided with the exercise rather than replacing it — same emulator action, same KVM rule, same
`emulator-options`.

**Fail fast, fail cheap**

- `ruff` and `mypy` run *before* the emulator: a lint error or a broken probe contract costs 30
  seconds, not a ten-minute boot
- `concurrency` cancels superseded runs; 40-minute job cap

**Don't race the device**

- Waits for `sys.boot_completed` *and* for the package manager to answer — an emulator reports
  "device" before it can install anything
- Appium started with a 40-attempt `/status` poll, not a blind `sleep`; on failure it tails
  `appium.log` and exits with a clear message instead of letting every test fail on a refused
  connection

**Remove sources of flake**

- KVM enabled — without it the emulator is ~10x slower and the job times out
- All three animation scales zeroed on the device, plus the action's own flag
- `hide_error_dialogs 1`, so a crash dialog cannot sit on top of the UI
- `implicitly_wait(0)` in the suite, so only explicit waits apply
- `--reruns 1` — one retry absorbs emulator noise; three would hide a real failure
- App installed once with `adb`, then `--no-install` so Appium does not reinstall it
- `POST_NOTIFICATIONS` granted two ways — `adb install -g` and `autoGrantPermissions` in the
  capabilities. It is a runtime permission on API 33+, and left ungranted the system dialog
  sits on top of the app and every locator lookup fails. Granting it in one place only would
  mean any change to how the app is installed reintroduces the dialog

**Structural**

- The whole run lives in one script, because the emulator action runs each inline `script:` line
  in its own shell. That is what caught a multi-line `for` loop in my first draft, which would
  have failed on the first run
- `set -euo pipefail`, `::group::` folding, and the pytest exit status preserved through cleanup
- Audio deliberately **not** disabled: `dumpsys audio` is one of the three playback signals

**Diagnosis when it fails**

- Artifacts on success *and* failure — the starter uploads only on failure. Allure report, raw
  results, `appium.log`, `logcat.txt`, 14-day retention
- Per-test screenshot, page source and logcat attached to the Allure result

**Deferred on purpose:** the booted-AVD snapshot cache, worth about four minutes a run. It is the
most likely thing to break a first attempt, and the requirement is a green run — hardening is
credit on top of that. Add it once the job is green and confirm it stays green.

### Known limitations

- **CI has never run.** The workflow is written and its YAML parses, but no GitHub Actions run
  has happened. Locally the suite is green on a physical handset and on an API 34 emulator,
  separately and in parallel — so the emulator itself is proven, the hosted job is not.
- **No audio content assertions.** `dumpsys audio` proves sound is being produced; nothing
  checks that you'd hear "fifteen" at 0:15. See "How playback is verified".
- **iOS runs have never happened.** Device discovery *is* implemented and verified against
  this machine — `simctl` for simulators, `xctrace` for physical devices. What has never been
  exercised is opening a session: there is no iOS build of MiniCast, so the page objects,
  locators and capabilities are untested.
- **Rotation is tested for playback continuity, not layout.** Landscape clips the lower Now
  Playing controls and does not scroll (BUG-012), and how much is lost depends on screen
  height — so asserting on them would make the test pass or fail by device. Layout stays
  manual, in TC-9.3.
- **Interruptions are not automated.** Real calls, audio focus loss and Bluetooth handover need
  a second phone. They stay manual, in `S8 - Interruptions`.
- **Two-device parallelism is proven, three or more is not.** Worker-to-device mapping is
  round-robin and the helper ports are offset per worker, but only `-n 2` has actually run.
